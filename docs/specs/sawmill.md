# Spec: Sawmill software factory

Source: `docs/sawmill_prd.md` (Oct 21, 2026). Published as [#1](https://github.com/markdlabrecque/sawmill/issues/1). Revised Oct 22, 2026 against two weeks of real sessions (`docs/analysis/usage-vs-sawmill.md`).

## Problem Statement

A developer has a queue of feature-sized tickets for internal tools and, later, products. Today every ticket needs them to set up a sandbox, write tests, write code, review it, rebase, merge, and report back. That is slow, interrupts other work, and the ticket thread rarely shows what actually happened. The human user wants to line up a batch of tickets, start a run, and come back to merged, tested code on an integration branch, and only be pulled in when an agent has a question or a ticket keeps failing.

## Solution

Sawmill: a run is a batch of tickets in blocked-by order, executed from a millyard (the project's designated worktree on its integration branch). `mill run` activates the run for the shared scheduler, whose deterministic orchestrator dispatches ready tickets up to the machine-wide slot limit. Each ticket has its own worktree and team (normally test writers, implementer, reviewer, with test writers omitted for `existing-checks` or `tests: none`) on an agent runtime (Claude Code, Pi or Codex) with a model and effort per role. Every deterministic step lives in the Mill CLI, including the orchestrator loop, the reporter step, and every state change. Agents never write state. The run file (`.mill/run.sqlite` in the millyard) is the source of truth for the run: membership, order, and each ticket's state (queued, blocked, working, done, logjam). The tracker mirrors local run changes through comments, labels, assignment and closure; it is not the source of run state. Explicit text refreshes and execution safety checks may read it during a run. A question from an agent, a failed tracker write, or an exhausted retry cap all land in logjam, and the human user answers through the CLI. Environment failures are retried without spending a bounce. Ordering comes only from the blocked-by graph, resolved once at draft time; independent tickets run in parallel in their own worktrees and the rebase gate resolves collisions. Approved work passes the rebase gate, goes up as a pull request or merge request against integration, waits for CI where the project has one, and is merged through the tracker when green. Promotion to main stays manual.

## User Stories

### Drafting a run

1. As the human user, I want `mill run draft` to take a label, a spec issue, or a list of ticket numbers, look the tickets up in the tracker, order them by their blocked-by links, and write the run file, so that I line up a batch in one command.
2. As the human user, I want draft to read the tracker's native blocking links where they exist (GitHub issue dependencies) and fall back to a "Blocked by" section in the body (GitLab), so that the tickets my to-tickets skill already writes work unchanged.
3. As the human user, I want draft to refuse a run where a ticket is blocked by an open ticket outside the run, naming it, so that nothing starts out of order and I can add the blocker or drop the ticket.
4. As the human user, I want draft to append to an unfinished run and refuse unsafe replacement, so that I cannot lose a run by accident.
5. As the human user, I want a `sawmill` Claude Code plugin with a `draft` skill that calls `mill run draft` and applies judgment on top (drop a ticket, split one, ask me about an odd dependency), so that `/sawmill:draft all tickets with label xyz` is enough to set up a run.
6. As the human user, I want `mill` invoked from any linked worktree to resolve the designated millyard, and `mill run draft` and `mill run` to refuse unless that millyard is on the integration branch and clean, so that every ticket worktree is cut from the right base.
6a. As the human user, I want `.mill/config.yaml` to carry a `name` key that I set by hand, used for the DDEV project name and the worktrees root layout, and I want every `mill` command to halt when it is missing, so that a sandbox is never named after a folder called `main`.
6b. As the human user, I want draft to assign every ticket in the run to me (the user the tracker CLI is logged in as), queued and mirrored like any other tracker write, skipping and naming any ticket someone else already holds, with each ticket's outcome kept in the run so status shows it, so that nobody starts a ticket Sawmill is about to work on.

### Running and watching

7. As the human user, I want `mill run` to activate the drafted run in the current millyard once and hand it to the shared scheduler, which keeps it going until every ticket is done or logjam, so that the factory runs unattended.
    - I want a drafted or replaced run to stay inactive until I start it, so that I can inspect it first.
    - I want an active run that is waiting on a dependency, an answer or a free slot to keep moving without another command, so that the run is never forgotten.
    - I want one scheduler to serve all my projects and give each a fair turn at the shared slots, so that one project cannot starve another.
    - I want `mill run stop` to stop a whole run from starting new tickets until I start it again, so that I can hold a project without touching its working tickets.
8. As the human user, I want `mill run status` to print one table containing only queued, working (with current role, bounce count, and time in stage), and logjam (with reason) tickets in their stored order, so that I can focus on current work without reading ticket threads. Done and blocked tickets remain stored but are not listed.
9. As the human user, I want `mill run status` to read only the run file, never the tracker, so that it is instant and works offline.
10. As the human user, I want `mill run stop <n>` to stop a working ticket at its next stage boundary with a WIP commit and put it in logjam with reason stopped, so that I can pull a bad run without killing processes.
11. As the human user, I want `mill team tail <n>` to follow the live log of the role currently running for a ticket, so that I can peek into a headless agent.
12. As the human user, I want every role's stream written to `.mill/logs/<ticket>/<role>-<round>.jsonl` and the runtime session id recorded in the run file and the reporter comment, so that I can open a finished role with the vendor's resume command and ask it questions.
13. As the human user, I want the scheduler to need no durability of its own: if it dies, I run `mill run` again and the new scheduler continues from the run files, keeping live workers and re-dispatching any ticket marked working whose team is no longer alive from that ticket's branch, so that there is no session state to protect.
14. As the human user, I want `mill run once` to perform a single dispatch pass without activating the run, so that I can watch one decision by hand and tests can drive the loop.

### Answering and finishing by hand

15. As an agent, I want to ask the human user a question by returning a question outcome, so that I never block silently.
16. As the human user, I want a question to stop the team completely rather than pause it, so that no process sits waiting on me.
17. As the human user, I want any changed files committed as a WIP commit on the ticket branch and pushed before the team exits, so that nothing an agent did is lost.
18. As the human user, I want the ticket marked logjam in the run file with the question and the stage reached, the worktree left in place, the report readable with `mill run log <n>`, and the logjam label mirrored to the tracker, so that I know why and where the team stopped and can see it from my phone.
19. As the human user, I want `mill run answer <n> "<text>"` to post my answer as a ticket comment, clear logjam, and re-queue the ticket, so that I never edit the tracker by hand to unblock a run. In an active run the scheduler picks it up. An answer never activates a draft, and `mill run answer` leaves a stopped run stopped. Only an answer given on the board (#93) also starts a stopped run.
20. As the human user, I want the re-dispatched team to start on the existing ticket branch with the ticket thread in its handoff, so that the agent sees the question and the answer.
    - On a `not-reproduced` stop, I want `mill run answer <n>` to re-run the final tests and carry on to the pull request and merge, and `mill run answer <n> --implementer "<text>"` to send it back to the implementer instead, so that a ticket whose code is fine can still finish through the tool.
21. As the human user, I want `mill run close <n>` to mark a ticket done in the run file and close it in the tracker, so that I can finish a ticket by hand and let its dependents proceed.
22. As the human user, I want a ticket that exhausts its retry cap to go to logjam with the last failure as the reason, so that I know why the factory stopped.
23. As the human user, I want a ticket whose worktree creation or post-create hook fails to go to logjam with reason environment and the hook output, so that I can fix the environment.
24. As the human user, I want all human-needed work in one state, logjam, mirrored as one label, so that I watch one queue.

### State and the tracker mirror

25. As the human user, I want only the `mill` CLI to ever write the run file, so that no agent judgment can drop or garble a state change.
26. As the human user, I want every state change written to the run file first and mirrored to the tracker second, so that the run file is never behind.
27. As the human user, I want a tracker write that fails three times with a short backoff to put the ticket in logjam with reason tracker, holding the unposted comment or label in the run file, so that the run never silently diverges from what the tracker shows.
28. As the human user, I want `mill run answer <n>` with no text to retry the held tracker writes for a tracker logjam and re-queue the ticket, so that an outage costs me one command per ticket.
29. As the human user, I want the CLI to record a report at every stage change (worktree created, tests written, implemented, review pass or bounce, rebase, CI wait, CI failed, merged, retry cap, infrastructure, stopped, aborted) in the run file, and `mill run log <n>` to print them in order, so that the ticket thread keeps only the outcome and the people's comments.
30. As the human user, I want the final reporter comment to summarise what changed, which tests were added, the merge commit, and the role session ids, so that I can skim the result without opening the diff.
31. As the human user, I want the reporter step to close the ticket after a successful merge, so that closed means merged.
32. As the human user, I want reporter comments and labels produced by deterministic CLI code rather than an agent, so that the mirror is consistent and costs nothing.
33. As the human user, I want `mill tickets label` and `mill tickets comment` available by hand, so that the reporter's primitives are mine too.

### Worktrees and hooks

34. As the orchestrator, I want `mill worktree create <n>` to cut a worktree from the millyard's integration branch on a branch named after the ticket and print its path, so that a team has an isolated sandbox.
35. As the orchestrator, I want `mill worktree create` to reuse an existing ticket branch and worktree when they exist, so that a re-dispatched ticket continues from its WIP commit.
37. As a project maintainer, I want worktrees to be plain git worktrees created beside the millyard, named by the bare ticket number, with a machine-wide `worktrees` root in `~/.config/sawmill/config.yaml` that puts them at `<root>/<name>/<ticket>` instead, so that a millyard at `code/main` gets `code/123` and I can keep every sandbox under one folder if I prefer.
38. As a project maintainer, I want a `setup.sh` hook that receives the worktree path and ticket ID as arguments and environment variables, so that I can start DDEV, install dependencies, and seed a database.
39. As a project maintainer, I want a non-zero exit from the post-create hook to fail the creation and tear the worktree down, so that no half-built sandbox reaches a team.
40. As a project maintainer, I want a `teardown.sh` hook that runs before the worktree is removed, so that I can stop containers and clean up.
41. As the orchestrator, I want `mill worktree remove <n>` to run the teardown hook and then remove the worktree, so that cleanup is always complete.
42. As the human user, I want `mill worktree gc` to remove every worktree whose ticket is done, running the pre-remove hook for each, so that aborted and hand-finished tickets do not leave sandboxes behind.
43. As the human user, I want to run the worktree commands by hand, so that I can debug a sandbox without the orchestrator.

### Agent runtime

44. As a project maintainer, I want to choose the agent runtime (Claude Code, Pi, or Codex) in project config, so that the factory is not tied to one vendor.
45. As a project maintainer, I want to set the model and effort for each role (test writers, implementer, reviewer) in project config, so that a cheap model writes tests, a strong model reviews, and a client project never runs on a model family I did not choose.
46. As the team runner, I want one runtime contract for all roles: a command run as a process in the worktree, given a role, a model, an effort and a handoff, returning a structured outcome, so that adding a runtime is one adapter.
48. As the human user, I want each role to run as a plain child process of the vendor CLI with the worktree as its working directory, with no relay, proxy, or control channel in between, so that worktrees and DDEV provide the isolation and nothing sits between the agent and the model.
49. As the team runner, I want a role that fails for environment reasons (runtime would not start, provider down, tool loop, test timeout) to return an infrastructure outcome and be retried a bounded number of times without spending a bounce, so that an outage does not look like bad work.
50. As the human user, I want the orchestrator to stop dispatching new tickets after three infrastructure failures in a row and resume when a dispatch succeeds, so that one outage does not logjam the whole run.
51. As the human user, I want role prompts to tell the agent to take the recommended option unless the choice is hard to undo, so that teams ask me rarely and only about things that matter.

### Team run

52. As the orchestrator, I want `mill team run <n>` to spawn the three roles in order inside a ticket's worktree, so that one command runs a ticket from tests to review.
53. As a test writer, I want the ticket body and the project's test command in my handoff, so that I can turn the ticket into failing tests.
54. As the implementer, I want the failing tests and the ticket in my handoff, so that I can make them pass.
55. As the implementer, I want to run the unit tests locally inside the worktree and commit at checkpoints, so that I know when I am done and a crash loses little.
56. As the human user, I want the team runner to detect when the implementer changed the test files the test writers produced, so that tests are not weakened to pass.
57. As the reviewer, I want the ticket plus the full diff on first review, so that I can judge the change against what was asked.
58. As the reviewer, I want to check that the ticket's scenario was actually exercised, not just that tests pass, so that green tests on untested behaviour do not slip through.
58a. As the human user, I want a ticket with a `## User test cases` section to have each case performed by the reviewer as the user, in a browser against the worktree's running site, so that the change is checked the way a person would check it.
58b. As the reviewer, I want a case the user cannot complete (an error, a dead control, a wrong result, lost data) to be a bounce naming the case and the step, and everything else (slow, unclear, could be better) to be a pass with recommendations, so that only broken experience stops a ticket.
58c. As the human user, I want the reviewer's user-testing recommendations posted on the ticket by the CLI as a `user-testing` comment, so that they are recorded where I read and never depend on an agent remembering to post.
58d. As the reviewer, I want re-review to run every case made stale by a repair, retaining completed cases only for unchanged code, prepared site, fixtures and case instructions, so that the fix is checked on the actual revision.
58e. As the human user, I want a ticket with user test cases on a project whose `test_harness` is `none` to be refused at draft time, naming the ticket, so that I decide up front rather than have the cases silently skipped.
59. As the reviewer, I want an unambiguous structured review outcome: pass, bounce, test-correction, question or infrastructure, with the evidence or explanation that outcome requires.
59a. As the implementer or reviewer, I want to send a scoped correction of a wrong protected test back to the test writers, followed by a fresh review, so that a test mistake does not stop the ticket for a person.
60. As the implementer, I want each bounce fix to be new commits appended after the bounce, as many checkpoint commits as I need, so that the re-review can be scoped to them without rewriting history.
61. As the reviewer, I want re-review to show only the repair's diff since the bounce, across all its commits, plus my original feedback, so that re-review stays cheap.
62. As the human user, I want a retry cap of three review rounds, so that a stuck ticket costs a bounded amount.
63. As the human user, I want `mill team review <n>` to run the reviewer alone against a worktree, so that I can get a review on hand-written work.
64. As the team runner, I want to run the reporter step after each role finishes, so that the ticket thread is updated without any agent remembering to do it.

### Rebase gate and merge

65. As the orchestrator, I want `mill integrate <n>` to rebase the ticket branch onto integration, run the full test suite, push, open a pull request or merge request against integration (reusing one that already exists for the branch), and merge it through the tracker once it is green, so that integration only ever receives tested code and every merge is visible as a PR or MR.
66. As the orchestrator, I want a rebase conflict or a test failure from `mill integrate` to count as one more implementer round, so that routine drift does not escalate to the human user.
67. As the human user, I want `mill integrate` to refuse to merge when tests fail, so that integration never goes red through the factory.
68. As the human user, I want `mill integrate` to run the test command under a project-configured timeout and report a timeout as an infrastructure outcome, so that a slow suite is never mistaken for a failing one or handed to the reviewer as a finding.
69. As the human user, I want `mill integrate` on a project with CI to wait for the pipeline on the PR or MR head commit before merging, so that "green" means what it means on my client projects and protected branches are respected.
70. As the orchestrator, I want a red pipeline to count as one more implementer round with the pipeline log in the handoff, so that CI-only failures are repaired like any other.
71. As the human user, I want promotion from integration to main to be manual and outside the factory, so that I control releases.
72. As the orchestrator, I want `mill integrate` to report merged, rebase conflict, tests failed, CI failed, or infrastructure distinctly, so that I know which path to take next.

### Orchestration

73. As the human user, I want the orchestrator to be ordinary CLI code and not an agent, so that dispatch decisions are predictable and free.
74. As the human user, I want the orchestrator to run at most a machine-wide number of tickets at a time, default two, so that the desktop and my Claude plan stay usable.
75. As the orchestrator, I want to dispatch ready tickets in run order until the slots are full, with no attempt to predict file collisions, so that the factory never idles with work available and conflicts are left to the rebase gate.
76. As the orchestrator, I want a queued ticket to become ready when every blocked-by link is satisfied locally: manual completion releases it, while a merged blocker must have reached the millyard. Remaining cleanup or tracker reporting need not finish first; no tracker lookup decides readiness.
77. As the orchestrator, I want to handle a team result (merged, logjam, infrastructure, stopped) by updating the run file and freeing the slot, so that the loop keeps moving.

### Configuration and project setup

78. As a project maintainer, I want project config in `.mill/config.yaml` in the millyard, kept out of git, naming the ticket backend and repo identity, agent runtime with a model and effort per role, test command and timeout, whether to wait for CI, and integration branch, so that each millyard self-describes without touching the repo.
78a. As a project maintainer, I want `mill build` to create the `.mill/` folder in the millyard, copy my default from `~/.config/sawmill/default.yaml` to `.mill/config.yaml`, and add `.mill/` to `.git/info/exclude`, so that a new millyard starts from my house settings in one command and nothing Sawmill-specific is ever committed.
78b. As a project maintainer, I want `mill build` to write the built-in template to `~/.config/sawmill/default.yaml` the first time, if it is missing, and to refuse to overwrite an existing `.mill/config.yaml` without `--force`, so that I always have a default to edit and never lose a tuned config.
78c. As a project maintainer, I want `mill build` to detect a DDEV project (`.ddev/`) or a Docker project (`docker-compose.yml`, `compose.yaml`, `Dockerfile`, or `.docker/`) and write `test_harness: ddev` or `test_harness: docker` into `.mill/config.yaml`, with DDEV winning when both are present, so that user testing is wired up without me remembering.
78d. As the human user, I want every `mill` command to abort with exit 2 when `.mill/config.yaml` has no `test_harness` key, telling me to add `test_harness: none` if I mean to opt out of user testing, so that skipping it is always an explicit choice.
78e. As the human user, I want config validation to report every problem it finds, one per line with the key and what is wrong, before exiting, so that I fix the file in one pass instead of one error per run.
78f. As a project maintainer with a project that has no tests, I want to write `tests: none` in `.mill/config.yaml` to opt out of tests on purpose, so that a ticket can go from draft to merge with no test writers, no red check and no local test run, while a missing `tests` key is still an error that tells me how to opt out.
79. As a project maintainer, I want machine-wide settings (concurrency, infrastructure retry count, pause threshold, worktrees root) in `~/.config/sawmill/config.yaml`, separate from project config, so that one desktop limit applies across projects.
80. As the human user, I want the same `mill` surface used by the orchestrator and by me, so that there is one way to do each thing.
81. As the human user, I want the ticket layer to work with GitHub Issues first, so that the first internal tool can run end to end.
82. As the human user, I want a second ticket backend for GitLab Issues with the same interface, so that client projects can use the factory.
83. As the human user, I want machine-readable output from every `mill` command on request, so that the orchestrator and the draft skill can parse results without scraping prose.

## Implementation Decisions

**Package and language.** One TypeScript package on Node exposing the `mill` CLI. Six internal modules surfaced as CLI subcommand groups: config (`.mill/config.yaml`, `mill build`), run (file, draft, loop, status, answer, close, stop), ticket layer, worktree manager, team runner, reporter. The orchestrator loop, the reporter step, and every state change are deterministic code in this package; none is an agent. A separate `sawmill` Claude Code plugin ships the `draft` skill.

**Millyard.** The project's designated integration-branch worktree, resolved even when `mill` is invoked from another linked worktree. Its `.mill/config.yaml` names the integration branch. `mill run draft` and `mill run` refuse unless the millyard is on that branch with a clean tree. Worktrees are cut from it; `mill integrate` merges into it and pushes. One millyard holds at most one current run, plus saved run history.

**The `.mill` folder.** Everything Sawmill keeps in a millyard lives in `.mill/` at its root, and the whole folder is kept out of git through `.git/info/exclude`, never `.gitignore`, so the repo's committed files are untouched. Contents: `config.yaml` (project config), `run.sqlite` (the run file), `setup.sh` and `teardown.sh` (hooks), `db.sql` (the database dump the default DDEV hook imports, optional), `logs/` (role streams). Worktrees do not get a `.mill/`; state lives only in the millyard, and hooks run from the millyard's `.mill/` with the worktree path as an argument.

**Run file.** `.mill/run.sqlite` in the millyard. Tables: `run` (id, created, base branch, source such as label or spec), `tickets` (number, title, position, state, reason, stage, bounces, session ids, worktree path, branch, merge commit, timestamps), `edges` (blocked, blocker), `pending_writes` (ticket, kind, payload, attempts), `log` (ticket, time, event). States: `queued`, `blocked`, `working`, `done`, `logjam`. For queued work, `blocked` is derived from unresolved blocked-by links. Manual completion satisfies a link; merge acceptance alone does not, until the millyard fast-forward makes the work locally available. Cleanup and tracker reporting may still be pending. Only the `mill` process writes the file. The draft skill writes it through `mill run draft`. `mill run clear` is the only run-removal command: it discards current membership, checkpoints and the run log without creating an archive or another run. The permanent `.mill/run-access.sqlite` deletion fence holds no run state and survives removal and subsequent drafting. Every Mill run connection (readers included) holds a shared transaction on this separate file for its entire lifetime; clear takes its exclusive transaction before opening the current run and retains it through validation, unlink, connection close and sidecar cleanup. This prevents an already-open writer, activation, dispatch, draft replacement or new draft from racing deletion. Missing-run opens never create an empty run, including on Node versions without SQLite URL support.

**SQLite removal.** Mill leaves the run in SQLite's default DELETE rollback-journal mode; it does not enable WAL. Clear also acquires an exclusive transaction on the run file, refusing concurrent external SQLite transactions. An externally WAL-configured run must first be checkpointed and returned to DELETE mode by SQLite itself, which refuses if other WAL connections remain; Mill never assumes WAL is enabled or blindly unlinks live WAL/SHM files. The run's device/inode is checked again before unlinking. The run connection closes and applicable `run.sqlite-journal`, `run.sqlite-wal` and `run.sqlite-shm` remnants are removed under the separate deletion fence, before another Mill connection can open or create the current run. Kernel locks release on process exit; the fence file must never be unlinked. Board/scheduler discovery skips absent runs and preserves other projects and registration.

**Draft.** `mill run draft --label <l> | --spec <n> | <numbers...>`. Reads each ticket from the backend. Blocked-by edges come from the backend's native dependency links where the backend has them (GitHub issue dependencies) and otherwise from a "Blocked by" Markdown section in the body (GitLab, and GitHub without dependencies). Edges to tickets outside the run are allowed only when the blocker is already closed; otherwise draft exits 1 naming the blocker. Closed tickets are not runnable work: label and spec drafts leave them out and list them as skipped in the run, and a closed ticket a draft left out counts as a satisfied blocker. Explicitly naming a closed ticket exits 1 with an explanation unless `--include-closed` is given; the run records that override, and it never reopens the tracker issue. A draft whose selection is all closed exits 1 and leaves the current run and its history unchanged. The drafted title, body and dependencies stay as drafted, with one exception: just before a ticket's first start, every dispatch path (`mill run once`, the scheduler, `mill run --foreground` and `mill team run`) reads its open/closed state again. A ticket closed since drafting starts no role and opens no PR or MR; it is marked done with reason `already-closed` and its dependants proceed. An `--include-closed` run starts it anyway. A failed state read leaves the ticket queued and counts as an infrastructure result toward the run's pause. Tickets that already started are not checked again on repair or resume. Position is a topological order, ties broken by ticket number. Draft appends new tickets to an unfinished run without resetting existing work or execution intent. `--replace` is permitted only for an inactive draft with no working or logjam tickets; a completed run is saved to history before creating a new inactive run. Draft also refuses (exit 1) when `test_harness` is `none` and any ticket in the run has a `## User test cases` section, naming the ticket, so the human user chooses between wiring a harness and dropping the cases. Output: the table from `mill run status`.

**State changes.** Every transition is one function in the run module, called by the loop, the team runner, `mill integrate`, or a hand command. It writes the run file in a transaction first, then queues the tracker mirror writes (reporter comment, label add or remove, close) in `pending_writes` and flushes them. A flush that fails is retried three times with a short backoff. If it still fails, the ticket moves to `logjam` with reason `tracker`, the payloads stay in `pending_writes`, and the team is not dispatched again until `mill run answer <n>` succeeds in flushing them. Tracker reads also support explicit text refresh/reset, first-start open/closed checks, and CI/change-request/merge or mirror-recovery safety checks. They never import run state from the tracker.

**Tracker mirror.** The outbound copy of committed run changes; distinct from tracker reads for text refreshes and execution safety. A reporter comment when the ticket ends done (the merged report), for the reviewer's user-testing notes, and for a report a person posts with `mill tickets comment <n> <text> --stage <stage>`; every other report stays in the run log. The `logjam` label added on logjam and removed on answer, close on merge or `mill run close`. No `running` label. Label names are configurable. The human user never needs to edit the tracker to move a run; the thread is for reading.

**Reporter step.** Records one report per stage change in the run file's `log` table; `mill run log <n> [--json]` prints a ticket's rows oldest first as `time [stage] -> state (reason)` with each report's full details, and any failed tracker write. A logjam posts no comment: it adds the `logjam` label, and its reason and report (an agent's question included) are read with `mill run log <n>`. A report that is posted has a fixed first line naming the stage, so a human and a parser can both read the thread. Stages: worktree-created, tests-written, implemented, user-testing (the reviewer's per-case results and recommendations), review-pass, review-bounce (with round number), rebase, pr-opened (with the PR or MR link), ci-wait, ci-failed, merged (with the merge commit and the PR or MR link), retry-cap, infrastructure (with the error and retry count), stopped, aborted (with reason and stage). The final summary is built from the git log, diffstat, the list of added test files, and the role session ids. Agents may post extra comments but never own the stage log.

**Questions stop the team.** When any role returns a question outcome, the team runner commits all changed files as a WIP commit on the ticket branch, pushes, moves the ticket to `logjam` with the question and the stage reached, runs the reporter step with stage `aborted`, and exits. The worktree is left in place. No process waits. The pre-remove hook does not run on abort.

**Unreproducible repairs stop the team.** In a repair round (not a rebase-conflict repair) the implementer may return a `no-change` outcome with a summary of the passing test output when it cannot reproduce the failure. It must leave HEAD and the worktree untouched. The team runner moves the ticket to `logjam` with reason `not-reproduced` and posts one `aborted` comment saying the failure could not be reproduced, so a person decides instead of the ticket bouncing again. The comment names both ways out. `mill run answer <n> [text]` treats the failure as not a code problem: it drops the repair, keeps the reviewer's approval of the untouched head, and resumes the team at integration, so the rebase, final tests, push, pull request and merge run again from the current branch. A failing re-run is an ordinary integration bounce: it counts toward the retry cap and returns to the implementer. `mill run answer <n> --implementer [text]` keeps the repair and sends the ticket back to the implementer, with the answer text in the ticket thread of its handoff.

**Final test environment.** `mill integrate` runs the test command without `MILL_WORKER_TOKEN` and without the hook variables (`MILL_TICKET`, `MILL_PROJECT`, `MILL_MILLYARD`, `MILL_WORKTREE`), as a plain `npm test` from a terminal would. The final run happens inside a team worker, whose environment carries its `MILL_WORKER_TOKEN`. With the token inherited, every `mill` process a test starts keeps it (`bin.ts` only sets a fresh one when none is set), and so does every lock taken in the test process itself. When a test kills such a process and a later command recovers its stale lock, `stopDescendants` stops and kills every process carrying that token born after the dead owner. That includes the `git`, `node` and `gh` children of other test files running in parallel. This matches the four failures on #36. In each one a child process failed with no stderr. Node already appends a failed child's stderr to its "Command failed" message, and the test run captures it. A killed child has no stderr to show. The test process group stays recorded as an owned process of the worker, so worker recovery still stops the run. Children that start their own session are no longer found by token. Hook variables are never set in a worker. They are removed anyway so that a coordinator started from a hook cannot leak them.

**Hand commands.** `mill run answer <n> [text] [--implementer]`: with text, posts it as a ticket comment; in all cases flushes `pending_writes`, removes the logjam label, and moves the ticket to `queued`. On a `not-reproduced` ticket it resumes at integration unless `--implementer` is given; the flag is refused on any other ticket. `mill run close <n>`: moves the ticket to `done` with no merge commit, closes it in the tracker; dependents become ready. `mill run stop <n>`: sets a stop flag; the team runner checks it at every stage boundary, makes a WIP commit, and exits with `stopped`; the ticket moves to `logjam` with reason `stopped`.

**Clearing the current run.** `mill run clear [--json]` uses ordinary linked-worktree millyard resolution and configuration validation, and accepts no ticket argument or force bypass. It removes an eligible inactive, stopped or completed current run only when execution is proven quiescent. It refuses active/paused runs, working tickets, live or uncertain worker/process ownership, run locks/connections, retained worker slots and pending tracker writes. A logjam alone is not live execution. Refusals preserve the saved run and unrelated resources, never signal workers and never stop the shared scheduler. Safe sequence: `mill run stop` to prevent new dispatch, `mill run stop <n>` for each working ticket, wait for safe stage boundaries and worker exit, then resolve held writes with `mill run answer <n>` while keeping the run stopped and retry clear. Inactive runs need no whole-run stop. There is no interactive confirmation. Existing history, attempt records, role/worker logs, configuration, hooks, environment files, worktrees, branches, tracker content and registry entries are retained. Unlike stop it discards the run; unlike reset it does not clean up a ticket; unlike draft replacement it neither archives nor creates another run. Missing and repeated clears are explicit successful no-ops, never empty SQLite files; a later draft creates a fresh inactive run. Text and JSON distinguish `removed`, `absent`, `refused`, `failed`; exits are 0 for removal/absence, 1 for safety refusals/operational failures, 2 for invalid usage/configuration. Use clear rather than manual SQLite deletion. See [Operating Mill](../operating-mill.md#removing-the-current-run).

**Refreshing drafted text.** `mill run refresh <n>` fetches the ticket's latest body and comments using the draft reader. It accepts queued, blocked and logjam tickets, refuses working tickets with the stop command, and leaves work, sessions, questions, bounces and state intact. `mill run reset <n>` fetches before deleting comments or work, then clears progress and requeues as before. Both rebuild the acceptance snapshot, carrying human waivers only by unchanged item text, remapped to the new IDs and snapshot. Removed items cease to apply; added items need proof. A refresh of changed text invalidates an earlier review approval. Each successful refresh, including reset, records a human action and a log entry; status shows its timestamp, requester and snapshot. A tracker fetch failure exits 1 with a clear message and leaves saved state, logs and work unchanged. Neither command re-reads blocked-by links or changes the drafted proof plan; those still require re-drafting.

**Resuming.** A `queued` ticket whose branch exists is dispatched with `mill worktree create`, which reuses the branch and the worktree if present, so the WIP commit is the starting point. The handoff to the first role includes the ticket thread so the agent sees the question and the answer. On `mill run` startup, any ticket in `working` whose recorded process is gone is moved back to `queued` and logged; its branch holds whatever was committed.

**Parallel dispatch.** The blocked-by graph is the only ordering. Each pass: compute ready tickets (queued, no undone blocker), sort by position, dispatch until the slots are full, each in its own worktree. No attempt is made to predict which files a ticket will touch; two weeks of real runs showed every collision resolved by a rebase and none prevented by prediction. A merge conflict costs one implementer round at the rebase gate.

**Run lifecycle.** The run row records activation (`activated`) and a run stop (`stopped`) as durable intent. Run state is derived from them, the loop progress and the tickets: `completed` when every ticket is done, otherwise `inactive` when never activated, `stopped` after `mill run stop`, `paused` while an infrastructure pause holds, and `active` otherwise. An active run may be waiting on dependencies, answers or capacity. `mill run draft` registers the millyard but writes a new run row without activation, so a draft, a replacement draft, an archived run and a run drafted before this column existed are all inactive. Registry membership and an old loop cursor never imply activation. `mill run` (and its alias `--background`) runs preflight, activates the run, registers the millyard, makes sure the scheduler is running and wakes it. Activating an inactive or stopped run starts fresh loop progress. Repeating it on an active run changes nothing, so a pause survives. If activation succeeds but the scheduler cannot start, the command says both and exits 1, and the activation stays for the next start. `mill run stop` without a ticket sets the stop and leaves working tickets alone. `mill run stop <n>` still stops one ticket at a boundary, and stopping a run that was never started is a usage error. `mill run answer` makes the ticket eligible and, in an active run with no foreground coordinator, starts and wakes the scheduler. It never activates a draft, overrides a run stop or clears a pause; an answer from the board (#93) is the only one that also starts a stopped run. `mill run once` and `mill team run` stay manual: same slots, claims and locks, never activation. `mill run --foreground` activates the run and runs the orchestrator for that run in the terminal under its `loop` lock, with fresh loop progress, until the run finishes, has no runnable work, pauses or is stopped. The scheduler skips a run whose `loop` lock is held.

**Shared scheduler.** One scheduler per machine and home (`~/.local/state/sawmill/scheduler/`). Ownership is a single row in `owner.sqlite`, claimed under SQLite's write lock: a live owner (PID plus process birth identity) wins, and a dead owner is replaced. Concurrent `mill run` commands may each launch a scheduler, but all but the winner exit at once and the commands report the winner. The scheduler exits when its ownership row is gone or names another process, or on `mill scheduler stop` (SIGTERM after the current pass). Workers are detached and survive it. Its log is `scheduler.log` in the same directory, and `mill scheduler status` and `mill run status` report whether it is available. It keeps the environment of the command that started it. Each pass first subscribes to the scheduler directory, the registry and the slots directory, then lists registered millyards and subscribes to each `.mill` directory, and only then rereads state. A notification only means "reread": SQLite rewrites the run file on commit, so a committed change wakes the scheduler, and a rollback or a duplicate event only costs a no-op reread. CLI commands also touch the `wake` file after their commit. A failed notification never affects the committed transaction. A fallback scan every two seconds covers lost events, a crash between commit and wake, and registrations made while no scheduler ran. A scheduler started with `MILL_SCHEDULER_WATCH=off` relies on that scan alone, for filesystems without change events. Bursts are coalesced, and idle passes write nothing, so the scheduler's own reads cause no wake loop. For each registered run that is not inactive or completed, a pass loads its config, recovers dead workers with the existing process-identity checks, and consumes results into the pause state. A run is runnable when it is active and has ready tickets, and when neither its `loop` lock (a foreground coordinator) nor its `integration` lock is held. Admission is round-robin: one launch attempt per runnable project per round, least recently served project first, through the ordinary `dispatchOnce` claim, slot lease, worker token and pending-write gates, until the machine-wide `concurrency` is reached. Within a run, ticket order and dependencies are unchanged. Preflight in the scheduler never waits for an integration lock. An unreadable run file, an invalid config or a failed preflight is logged and that project is retried after a back-off, without stalling the others.

**Orchestrator loop.** Whether run by the scheduler or `--foreground`, each pass recovers dead workers, consumes finished results, dispatches ready tickets up to the free slots, then waits for a change. `mill run once` does one dispatch pass and returns. If three dispatches in a row end in `infrastructure`, the run is paused: nothing new is dispatched while live teams are waited on, and the next successful team exit clears the pause. Scheduler restarts and repeated `mill run` keep it; `mill run stop` then `mill run`, or `mill run --foreground`, retries queued work. Concurrency and the pause threshold are machine settings; concurrency defaults to two.

**Status.** `mill run status` reads the run file only, plus the scheduler's ownership row. A first line gives the run state and whether the scheduler is running, then one table: ticket, title, state, detail. Only `queued`, `working`, and `logjam` tickets are listed, in their stored order. Detail is role, round and time in stage for working; reason for logjam. Ticket-specific supplementary notes use the same allowlist, and the historical skipped-closed listing is omitted. `--json` applies the same allowlist to `tickets`, retaining the response schema and run/scheduler metadata, including `run.lifecycle` and `scheduler` (`available`, and `pid` when available). With no matching tickets, text keeps the run/scheduler line and table header and JSON has `tickets: []`; the real lifecycle, including `completed`, is unchanged. This read-only presentation filter does not alter stored tickets, history, blocked-by resolution, shared readers/formatters, the board, or scheduler behavior.

**Logs and peeking.** The team runner invokes the runtime with streaming output and tees the stream to `.mill/logs/<ticket>/<role>-<round>.jsonl`. `mill team tail <n>` follows the newest log for the ticket and prints events readably. The runtime adapter extracts the vendor session id and the team runner stores it in the run file; the reporter includes it so the human user can run the vendor's resume command (for Claude Code, `claude --resume <id>` in the worktree).

**Worktrees.** `mill worktree create <n>` runs `git worktree add` with the worktree named by the bare ticket number, cut from the integration branch on branch `mill/<n>`. By default it is a sibling of the millyard: for a millyard at `~/Projects/islandhealth/code/main`, ticket 123 is at `~/Projects/islandhealth/code/123`. If the machine config sets `worktrees: /home/me/sandboxes`, it is at `/home/me/sandboxes/<name>/123` instead, where `<name>` is the `name` key from `.mill/config.yaml`. The project name never comes from a folder name. The branch and the worktree are reused if they exist. The ticket number plus the project name is what every hook and harness uses for the sandbox: the DDEV project is `123-islandhealth`, so `https://123-islandhealth.ddev.site`. `mill worktree remove <n>` runs the teardown hook, then `git worktree remove`, and deletes the `mill/<n>` branch only if it was merged. There is no provider abstraction: Sawmill is the only thing that creates or removes its worktrees, so hooks always run.

**Hooks.** `.mill/setup.sh` runs after a worktree is created; `.mill/teardown.sh` runs before one is removed. Each receives the worktree path and ticket number as positional arguments (`$1`, `$2`) and as `MILL_WORKTREE`, `MILL_TICKET`, `MILL_PROJECT` (the `name` key from `.mill/config.yaml`), and `MILL_MILLYARD` (the millyard path). `mill build` always creates both hooks, so they are there to edit; a hook that is still missing is a no-op. Setup failure removes the worktree and reports the hook's output; the ticket moves to `logjam` with reason `environment`.

**Default DDEV hooks.** The package ships `templates/ddev.setup.sh` and `templates/ddev.teardown.sh`. `mill build` seeds them to `~/.config/sawmill/ddev.setup.sh` and `ddev.teardown.sh` if missing, and when `test_harness` is `ddev` copies them to `.mill/setup.sh` and `.mill/teardown.sh` unless those already exist. The setup script: has a `DB_PATH` constant at the top, defaulting to `$MILL_MILLYARD/.mill/db.sql`, which the human user may change (a missing file skips the import); writes `.ddev/config.local.yaml` in the worktree with `name: <ticket>-<project>`; runs `ddev start`; runs `ddev composer install` when `composer.json` is present; imports the database from `DB_PATH`. Both run with `set -euo pipefail` so any step failing fails the hook. The teardown script checks `ddev describe <ticket>-<project>` and, if the project exists, runs `ddev delete -yO <ticket>-<project>` so no orphaned DDEV project or containers survive the worktree; a project DDEV does not know about is a no-op. `mill worktree remove` and `mill worktree gc` run it before the provider removes the worktree.

**Default blank hooks.** The package also ships `templates/setup.sh` and `templates/teardown.sh`. `mill build` seeds them to `~/.config/sawmill/setup.sh` and `teardown.sh` if missing, and when `test_harness` is not `ddev` copies them to `.mill/setup.sh` and `.mill/teardown.sh` with mode 755 unless those already exist. They run with `set -euo pipefail` and have no active commands: comments say when each runs, what it receives, that a non-zero exit fails it, and give a commented example (`npm ci` for setup).

**Agent runtime contract.** Project config names a runtime: `claude-code`, `pi`, or `codex`, and for each role a model and an effort. The team runner invokes the runtime once per role as a child process with the worktree as working directory, passing the role name, the role's model and effort, and a handoff document (ticket, prior role outputs, test command, pipeline log when repairing CI, ticket thread when resuming). Each role's prompt is a Markdown file shipped in the package under `roles/` (`test-writers.md`, `implementer.md`, `reviewer.md`); the team runner sends the prompt followed by the handoff. A role ends its work by printing one fenced block tagged `mill-outcome` containing a JSON object with an `outcome` field and the fields that outcome needs; the adapter parses the last such block and treats a missing or malformed one as `infrastructure`. The runtime adapter turns that into the tool's own invocation, limits tools per role with the tool's own flags, and parses the result into one structured outcome: `done` (with a short summary), `bounce` (reviewer only, with feedback and, when user test cases were run, the failed cases), `pass` (reviewer only, with optional user-testing recommendations), `test-correction` (implementer or reviewer, naming protected files, the mistake and preserved requirements), `no-change` (implementer repair only, with passing test evidence and no changes), `question` (with the question text), or `infrastructure` (with the error: process failed to start, non-zero exit with no result, provider or auth error, the same tool error repeated more than a small fixed number of times, or no result within the role timeout). Nothing sits between the adapter and the vendor CLI: no relay, no proxy, no control channel. The Claude Code adapter is built first; Pi and Codex follow. Role prompts instruct the agent to take the recommended option on any choice unless it is hard to undo, and to ask only then.

**`mill integrate`.** Rebase the ticket branch onto integration and run the project test command in the worktree under the project test timeout (default 30 minutes). On green, force-push the rebased `mill/<n>` branch and open a pull request (GitHub) or merge request (GitLab) from it against the integration branch, titled from the ticket and linking it; if one already exists for the branch, reuse it. When `ci: wait`, poll the tracker every `ci_poll_interval` for the pipeline on the PR or MR head commit. When the pipeline passes, or at once when `ci: none`, merge the PR or MR through the tracker API with the project's `merge_method` (default `squash`), delete the remote ticket branch, and fast-forward the millyard. Conflict aborts the rebase and returns `rebase-conflict`; red tests return `tests-failed`; a red pipeline returns `ci-failed` with the log URL; a test timeout, an unreachable tracker, or a merge the tracker refuses for a reason that is not a failing check returns `infrastructure`. The first three are fed back to the implementer as one more round, counted against the retry cap; a CI repair is pushed to the same branch so the same PR or MR picks it up. `infrastructure` is retried without spending a round. Merge never happens on a head commit whose pipeline did not pass. Nothing is ever merged locally and pushed to integration, so protected branches work as they are. With `tests: none`, the local test run is skipped and the rebased head goes straight on to push; the PR or MR body and the merge report say tests were skipped by config instead of "Local tests passed". Projects may declare `required_checks` (`clean`, `build`, `lint`, `typecheck`, with a `timeout`); after the test run, or in its place with `tests: none`, Mill runs each with `bash -c` in that order on the rebased head. A non-zero exit, a missing command included, returns `checks-failed` with the output and counts as one more implementer round, unless the output names only protected test files, which makes it a test correction for the test-writers; a timeout or a check that changes HEAD or the worktree returns `infrastructure`. The evidence (command, exit, duration, head) is reset by every rebase, required before merge, and listed in the PR or MR body and merge report. Advisory `checks` and focused test runs never satisfy a required check. A project may also declare an `artifact` required check, run last, that smokes the actual installable or build artifact rather than the source tree.

**`mill release handoff <n>`.** Read-only, and refused until the ticket is merged. It reports the delivered revision, merge commit and base, the `artifact` check and the head it passed on, each acceptance item as verified, waived or pending, and each project-declared `release.steps` entry as verified (its named required check passed on the delivered head), pending, or not applicable (its `paths` miss the delivered change). Recovery groups the applicable steps as reversible, separately recoverable or irreversible, shows a rollback command only when the project declared one, and says that reverting the merge commit undoes code only. `releaseReady` is true only when nothing applicable is pending; `deployed` is always false, since Mill never deploys.

**Team runner.** Roles run one at a time. Flow: test writers, implementer, reviewer; on bounce, implementer appends one or more fix commits and reviewer re-reviews with only the repair's diff since the bounce and its own prior feedback; after three bounces the team exits with `retry-cap` and the ticket moves to `logjam`. Answering a `retry-cap` ticket gives it one more round: the bounce count drops to two, the implementer gets the last feedback and the answer, and another bounce stops it again. On pass, the team runner calls `mill integrate`; on conflict, test failure or CI failure it runs one more implementer round. After the test writers, and before the implementer starts, the team runner runs the project test command in the worktree under the project test timeout, the same way `mill integrate` does. If the run exits 0, the tests guard nothing: the test writers run again with fixed feedback asking for tests that fail until the ticket is built, the ticket thread gets a `tests-not-red` comment, and no person is asked. These send-backs are counted separately from bounces; after two, a third green run stops the ticket in `logjam` with reason `tests-not-red` and the test output, without running the implementer. A timed-out or killed run is `infrastructure`, not green. A stop or crash during this check runs it again on resume. After the implementer, the team runner compares the test files the test writers committed against the current tree and treats a change as a bounce with fixed feedback. When a protected test is wrong, the implementer or reviewer returns `test-correction` without changing the protected tests: the files, the mistake, and how the corrected tests still cover the ticket. The test writers get that request and the implementation diff in the same worktree. The CLI starts each attempt from the protected tests by reverting, in a new commit, any rejected change to any protected file, not only the files the new request names; the reviewer's correction diff covers every protected file. It refuses an attempt that leaves uncommitted files, rewrites history, or changes anything outside the named files. It then runs the tests and records the result, and the reviewer reviews again. Only a passing review moves the protected baseline to the correction commit, keeping the original writer commits for rebase checks. A pending correction voids any earlier approval: `mill integrate` refuses while one is pending, and the team runner sends it to review first. A standalone `mill team review` cannot route a correction, so a `test-correction` there stops the ticket with a question carrying the request. Corrections are counted separately from bounces: after two attempts, a third request stops the ticket with a question. `mill run approve-tests <n>` stays the manual path for a person. An `infrastructure` outcome from any role or from `mill integrate` is retried up to three times with a short backoff, without touching the bounce count; if the retries run out the team exits with `infrastructure` and the ticket moves to `logjam` with reason `environment`. The stop flag is checked at every stage boundary. `mill team review <n>` runs the reviewer step alone. With `tests: none` the flow starts at the implementer: there are no test writers and so no red check, no role is handed a test run or allowed a test command, and the implementer's and reviewer's handoffs say the project has no tests.

**User testing.** If the ticket body has a `## User test cases` section (named cases as top-level list items or `###` headings), the team runner adds it to the reviewer's handoff together with the site URL (from `ddev describe` in the worktree when `test_harness` is `ddev`, or `test_url` when `docker`) and grants the reviewer the `chrome-devtools-axi` CLI for that run (allowed through the runtime's tool permissions; chosen over Playwright MCP for token cost). The reviewer performs each case as the user and reports per case: completed, or broken with the step that failed. Broken means the user cannot complete the case: an error, a dead control, a wrong result, lost data. Any broken case makes the outcome `bounce`, with the case and step in the feedback. Otherwise the outcome is `pass`, and anything the reviewer noticed (slow, unclear, could be better) goes in its recommendations. The team runner posts the per-case results and recommendations through the reporter as a `user-testing` comment; the reviewer never posts them itself. On re-review, the reviewer runs exactly the handoff's cases: any change to the reviewed commit, prepared site or fixtures makes earlier results stale and reruns every case. Only completed cases with unchanged code, site, fixtures and case instructions carry forward. Without the section, the browser CLI is not allowed and nothing changes.

**CLI output contract.** Every command supports `--json`. Human output is text on stdout. Exit codes: 0 success, 1 expected failure the caller should handle (tests failed, rebase conflict, bounce, aborted, logjam, draft refused), 2 usage or configuration error. `mill integrate` reports `merged`, `rebase-conflict`, `tests-failed`, `checks-failed`, `ci-failed`, `infrastructure`. `mill team run` reports `passed`, `retry-cap`, `aborted` (with reason and stage), `infrastructure` (with the last error), `stopped`.

**Ticket layer interface.** A backend implements: list issues by label, get one ticket (number, title, body, labels, state, comments, native blocked-by numbers when supported), add label, remove label, add comment, close, get pipeline status for a commit (`pending`, `passed`, `failed`, `none`, plus a log URL), find or open a pull request or merge request from a branch to a base (returning its id and head commit), merge it with a given method, and delete a remote branch. The interface is written against both GitHub and GitLab from the first commit so GitHub-only ideas (closing keywords, PR semantics) never leak into it. GitHub implementation first, GitLab second, selected by project config.

**Configuration.** Project config is `.mill/config.yaml` in the millyard, never committed. Keys: `name` (the project name; required, no default, never guessed; used for the DDEV project `<ticket>-<name>` and the worktrees root layout), `tracker` (`backend`: `github` or `gitlab`; `repo`; optional `host` for self-hosted GitLab), `integration` (branch name), `runtime` (`claude-code`, `pi`, or `codex`), `roles` (for each of `test-writers`, `implementer`, `reviewer`: `model` and `effort`, effort one of `low`, `medium`, `high`, `max`), `role_timeout` (default 60 minutes; exceeding it is an infrastructure outcome), `tests` (`command` and `timeout`, default 30 minutes), `ci` (`wait` or `none`), `ci_checks` (optional, GitHub with `ci: wait` only: `required`, check names that must each report and pass on the exact head, absent or pending ones keeping the pipeline pending and any failed run of a name failing it; `advisory`, names whose failure never blocks; every other check still gates; a name cannot be both, and GitLab refuses the key because its own pipeline rules gate the merge; `mill run draft` adds the integration branch's required status checks read from rulesets and branch protection, refuses with `ci: wait` when it finds neither those nor `ci_checks` and names the setting and permission to fix, refuses a GitHub merge queue or a GitLab merged results pipeline or merge train as unsupported, reports settings it could not read as not verified, and records the policy on the run; the PR body and merge report state it and its source), `merge_method` (`squash` or `merge`, default `squash`), `test_harness` (`ddev`, `docker`, or `none`; required, no default), `test_url` (required when `test_harness` is `docker`; for `ddev` it is read from `ddev describe` in the worktree), `labels` (name overrides; only `logjam`). Validation checks the whole file and reports every infraction, one per line naming the key and the problem (missing, unknown key, bad value, bad type), then exits 2 if there was any. It never stops at the first. Missing `name` and missing `test_harness` are infractions like any other; the `test_harness` line adds that `test_harness: none` is the way to opt out of user testing on purpose. The machine config is validated the same way, in the same pass, and its infractions are listed with the file they came from. `mill build` runs this validation on the file it just wrote and shows the list as its "still needs filling in" output. Machine config is `~/.config/sawmill/config.yaml`: `concurrency` (default two), `infrastructure_retries` (default three), `pause_threshold` (default three), `worktrees` (optional root; absent means the sibling `<project>.worktrees` directory), `ci_poll_interval` (default 30 seconds; how often the CI wait asks the tracker for pipeline status, the only place `mill` polls). The package ships both files as templates, `templates/default.yaml` and `templates/config.yaml`, with every valid key present and documented in comments; optional keys are commented out.

**`mill build`.** Creates `.mill/` in the current millyard, adds `.mill/` to `.git/info/exclude`, and writes `.mill/config.yaml` by copying `~/.config/sawmill/default.yaml`. If that default is missing, `mill build` first writes `templates/default.yaml` there; if `~/.config/sawmill/config.yaml` is missing it writes `templates/config.yaml` there too, so the human user always has documented defaults to tune. It refuses (exit 1) to overwrite an existing `.mill/config.yaml` unless `--force` is given. Before writing, it inspects the millyard: a `.ddev/` directory means `test_harness: ddev`; a `docker-compose.yml`, `compose.yaml`, `Dockerfile`, or `.docker/` means `test_harness: docker`; both means `ddev`; neither leaves the key absent and prints the opt-out instruction. It always installs `.mill/setup.sh` and `.mill/teardown.sh` unless those are already there, even with `--force`: the default DDEV hooks when it writes `ddev`, the default blank hooks otherwise. The choice is a snapshot of the project at build time; existing hooks are never replaced, so switching hooks after the project changes is up to the human user. It validates the result and prints what still needs filling in (at least `name` and the tracker repo identity, `test_harness` when nothing was detected, the hooks it created, and `.mill/db.sql` if the DDEV hook was installed).

**Sawmill plugin.** A Claude Code plugin named `sawmill` with one skill, `draft`. The skill takes a natural-language selection ("all tickets with label xyz", "the children of #40", "#12 #14 #15"), runs `mill run draft --json` with the matching flags, reads the result, and applies judgment: asks the human user about a blocker outside the run, suggests dropping a ticket that looks too big, or splitting one. It then shows the status table. It never writes the run file itself, and it never starts the run: the draft stays inactive until the human user runs `mill run`.

**Build order.** Bottom-up: `.mill/` and `mill build`; run file and `mill run draft` with the two-backend ticket interface and the GitHub implementation; worktree manager with `gc` and `mill integrate` (timeout, CI wait); team runner with the Claude Code adapter, per-role models, logs and `tail`, one role at a time then chained; `mill run` loop with status, answer, close, stop and the environment pause; the `sawmill` plugin; then Pi and Codex adapters and the GitLab backend; then one real run on an internal tool and one on a client ticket into its integration branch.

## Testing Decisions

**What makes a good test.** A test drives a `mill` command and asserts on what the outside world can see: stdout or JSON, exit code, run file rows, git state, tracker state, hook side effects. It never asserts on internal calls or module structure.

**Seam.** One seam: the `mill` CLI entry point, invoked in-process with injectable ticket backend and agent runtime, against a temporary millyard.

- Ticket backend: an in-memory fake implementing the same interface as GitHub and GitLab, including native blocked-by links, a scriptable pipeline status per commit, and a switch that makes writes fail. Tests seed tickets with blocking links or "Blocked by" sections and labels, then assert the resulting tracker state and comments.
- Run file: real SQLite in the temporary millyard, asserted through `mill run status --json`.
- Git: real. Each test creates a temporary repo with an integration branch and a bare remote, and asserts on real branches, commits, pushes, and worktrees.
- Hooks: real shell scripts written into a temporary directory by the test, so hook argument passing, exit codes, and output capture are exercised for real.
- Agent runtime: a scripted fake adapter that returns a fixed outcome per role invocation (done, pass, bounce with feedback, question, infrastructure), may write files into the worktree, emits a fake stream and session id, and records the model and effort it was given. This lets the team runner and orchestrator be tested without a model.

**What is tested.** Build: creates `.mill/config.yaml` from the user default, seeds the default from the built-in template when missing, refuses to overwrite without `--force`, detects `.ddev/` as `ddev`, Docker files as `docker`, both as `ddev`, neither as absent; other commands exit 2 without a valid `.mill/config.yaml`; a file missing `name` and `test_harness` with an unknown key and a bad `effort` value yields one exit 2 listing all four, with the opt-out hint on the `test_harness` line; `tests: none` is accepted, a missing `tests` key is still rejected with the `tests: none` hint, and the default template explains the opt-out above the `tests:` block; with `ddev` detected, the default hooks land at `.mill/setup.sh` and `.mill/teardown.sh`, existing hooks are left alone, and `.mill/` is in `.git/info/exclude`. Worktree naming: a millyard at `code/main` with `name: islandhealth` puts ticket 155 at `code/155` on branch `mill/155` by default, and at `<root>/islandhealth/155` when the machine config sets `worktrees`; `MILL_PROJECT` is `islandhealth`, never `main`; and hooks receive `$1`, `$2`, `MILL_WORKTREE`, `MILL_TICKET`, `MILL_PROJECT`, `MILL_MILLYARD`. The default DDEV hook is run against a fake `ddev` on `PATH` that records its calls: config.local.yaml written with the `<ticket>-<project>` name, start called, composer install only with `composer.json`, import only when the `DB_PATH` file exists, non-zero exit on any failing step. The default DDEV teardown hook against the same fake: `ddev delete -yO <ticket>-<project>` when describe succeeds, nothing when it does not. Draft: ordering from native links and from body sections, refusal on an open outside blocker, refusal over a live run, `--replace`, refusal of a user-test-cases ticket when `test_harness` is `none`. User testing: the section and site URL reach the reviewer's handoff with browser tools only when present; a fake reviewer returning a broken case yields a bounce naming the case and a `user-testing` comment; a pass with recommendations yields the comment and no bounce; a re-review after a user-testing bounce lists the failed cases in the handoff. Millyard checks (wrong branch, dirty tree). Label and comment commands. Worktree create, remove and gc, including setup failure cleanup, branch and worktree reuse, and merged-branch deletion on remove. `mill integrate` across merged (fake backend records the PR or MR opened, merged with the configured method, remote branch deleted, millyard fast-forwarded), PR or MR reuse on a second run, rebase-conflict, tests-failed, ci-failed (fake pipeline red on the PR head), merged-after-ci-wait (fake pipeline pending then passed), and infrastructure (test command exceeds the timeout; tracker refuses the merge). With `tests: none`, a ticket goes from draft to merge with no test run and no `tests-not-red`, and the PR body and merge report say tests were skipped. Outcome parsing: the last `mill-outcome` block wins, a missing or malformed block is `infrastructure`. Team runner bounce loop, retry cap, test-file tampering, per-role model and effort reaching the adapter, infrastructure retries not counting as bounces and exhausting to logjam, log file written and session id recorded, stop flag honoured at a stage boundary, and question abort (WIP commit present on the remote, reporter comment, logjam label, run file row). State changes: run file written before the mirror; tracker write failure retried then logjam with reason tracker and payloads held; `mill run answer` flushing them. Hand commands: answer re-queues and comments, close marks done and closes, dependents become ready. Loop: parallel dispatch of independent tickets in run order, the concurrency limit, the environment pause after repeated infrastructure failures, restart with an orphaned working ticket re-queued. Scheduler, driven through detached `mill` processes with scripted workers: a draft stays inactive through an answer and `mill run once`; the first `mill run` activates the run and one scheduler takes the ticket; simultaneous starts leave one scheduler and one claim; an unblocked dependent starts without another command and the run completes; a run stop holds against a CLI answer until `mill run`; an infrastructure pause survives a scheduler restart; a killed scheduler is reported unavailable and its replacement adopts the live worker without a second claim; two projects under a capacity of one take turns.

**Prior art.** None: the repo is empty. Use the Node test runner or vitest with temporary directories; a small helper builds a seeded temp millyard, bare remote and fake backend per test.

**Not tested.** Real GitHub or GitLab API calls (backends are thin adapters; one smoke test by hand before first real run). The real Pi, Codex, or Claude Code adapters beyond parsing a captured sample of their output. The `draft` skill's judgment; the CLI it calls is tested.

## Out of Scope

- Promotion from integration to main.
- Human review or approval on the PR or MR; it exists for CI and for the record, and Sawmill merges it.
- A chat channel for logjam answers.
- Reading run state back from the tracker; the tracker is a mirror.
- Predicting file collisions between tickets (touch points or path labels); the rebase gate handles conflicts.
- A human approval step before merge into integration; the human verifies on the integration branch, outside the factory.
- Running several agents in parallel within one ticket.
- Pausing or resuming a live agent process; a question always ends the team.
- More than one run per millyard at a time.
- Product deployment and polish; the pipeline is the same, only the last mile differs.
- Any UI beyond the CLI, the logs, the ticket thread, and the board in `docs/specs/live-view.md`, whose run controls call the CLI's own operations.
- Integration with T3 Code, Orca, or Herdr, whether for worktrees, agent sessions, or control. Those tools exist to put an interactive agent in front of a person. Sawmill's roles are non-interactive: they run headless as child processes, report through logs and the ticket thread, and are reopened with the vendor's resume command. There is nothing for those tools to show or control.
- A custom runtime command; the three built-in adapters are the runtimes until one is needed.
- Automatic creation of the integration branch or of tracker labels.

## Further Notes

- The accepted trade-off from the PRD stands: a narrow re-review can miss a fix that breaks already-approved code, and the rebase gate is the safety net.
- The run file replaces the PRD's "no local database" principle. The reason v1 and v2 of the orchestration project drifted was that agents owned state updates. Here every state change is CLI code, written locally first and mirrored second, so the file cannot fall behind and a failed mirror is visible as a logjam rather than a silent gap.
- Every merge goes through a PR or MR so protected integration branches on client projects need no exception, and the record of what merged is where the team already looks.
- Blocked-by edges are resolved once at draft time from native links or the body section, so both backends produce the same graph and the loop never reads the tracker.
- The test-file tampering check is cheap and closes an obvious hole in "write failing tests, then make them pass".
- Touch points were dropped after reviewing two weeks of real runs (`docs/analysis/usage-vs-sawmill.md`): no collision was ever prevented by prediction and every conflict was resolved by a rebase. The same review added the CI wait, per-role models, the infrastructure outcome, the test timeout, `mill worktree gc`, role logs with `tail`, the stop command, the ask-less rule, and a default concurrency of two, each traced to a recurring cost in those runs.

## Troubleshooting

- A role ends as `[sawmill:aborted]` with "Bash is denied". Roles run with `--permission-mode dontAsk` and an exact-match Bash allowlist (`src/claude-runtime.ts`, `src/pi-policy.ts`). Chained commands, `cd`, heredocs, and test commands with extra arguments are denied. Seen on #36: the test writer used `cat > file <<EOF` and `cd ... &&`, was denied, assumed all of Bash was off, and stopped without ever trying `npm test` or `git commit`. The role prompts now list the allowed tools (`roles/*.md`, "Your tools"). Do not widen the allowlist to fix this.
- Not yet done: a denied tool call still surfaces as a `question` outcome and a logjam comment. The runtime should detect a permission denial, tell the role which commands are allowed, and retry once before reporting. Only a repeated denial of an allowed command (the exact test command or `git commit`) should become a logjam. Revisit if the prompt change does not stop these aborts.

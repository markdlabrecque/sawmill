# Claude transcript audit evidence

This is the Claude/Mill part of the delivery-integrity audit. The strongest observed safeguard is the independent reviewer demanding proof through real Git, processes, HTTP and CLI boundaries. The most serious weakness is that a reviewer can return `pass` while declaring required acceptance work incomplete. Budget limits, role permissions and environment failures sometimes push necessary work into recommendations, which the delivery system can then leave behind.

All findings below distinguish historical incidents from current behavior. This report changes no product code, run state, tracker records or production systems.

## Acceptance must remain independent of retry budgets

On [#46](https://github.com/markdlabrecque/sawmill/issues/46), the final reviewer wrote:

> I'm passing this, but `npm test` failed in all three of my runs in this worktree, so the implementer's "422 green, 0 failures" didn't hold up for me.

The structured `pass` explained:

> Not bounced, because a third bounce would end the ticket over the environment problem the ticket targets.

Its recommendations included:

> Done-when #2 (final run and worktree run agree) is not met yet.

The same verdict reported an unproven environmental diagnosis and a missing token regression test. See the [native final response](/home/mark/.claude/projects/-home-mark-Projects-sawmill-code-46/429b86cc-e0fc-4850-8fc8-88fe9acab32c.jsonl:105) and [saved verdict](/home/mark/Projects/sawmill/code/develop/.mill/logs/46/reviewer-3.jsonl.meta.json:1). The worker-environment fault was subsequently addressed; this is evidence about verdict integrity, not a claim that the original fault remains.

The current [reviewer instructions](/home/mark/Projects/sawmill/code/audit/roles/reviewer.md:27) say to bounce wrong, incomplete or unproven work, then warn that three bounces end the ticket and should not be spent on something that can pass with a note. The observed verdict shows that warning can influence truth of acceptance.

This is repeated beyond that incident. [#90's pass](/home/mark/Projects/sawmill/code/develop/.mill/logs/90/reviewer-3.jsonl.meta.json:1) says the required ten-run comparison was "OUTSTANDING and not waived" and must happen before completion. [#115's pass](/home/mark/Projects/sawmill/code/develop/.mill/logs/115/reviewer-2.jsonl.meta.json:1) leaves a requested regression test absent because the implementer cannot edit the protected file, accepting code reading instead. Some deferred work may later have been done by a person; the role verdict itself does not establish that.

Recommendation: store each required acceptance item as verified, explicitly waived by an authorized person, or pending, with evidence tied to the reviewed commit. A pending required item should block delivery or hand control to a person. Retry budgets should choose the next actor or stop the run; they should never change an incomplete verdict into a pass. Separate environment-blocked, missing proof and product failure so each has an appropriate recovery path. Provide a route to add missing protected coverage without weakening existing coverage. The proposed completion threshold is zero pending required acceptance items, with every waiver recorded explicitly and every verification linked to the delivered commit. An exhausted retry budget is not a waiver.

## Browser verification exists but was not exercised here

There are zero nonempty `cases` arrays across all 266 outcomes, including all 88 reviewer outcomes. There are also zero actual `Cases to run, return each exact case name once:` handoffs in those invocations' native initial prompts. The real millyard currently has [test_harness: none](/home/mark/Projects/sawmill/code/develop/.mill/config.yaml:71), while retaining `npm test` and `ci: wait`. This is a browser/site verification opt-out, not the separate `tests: none` option. The current [reviewer prompt](/home/mark/Projects/sawmill/code/audit/roles/reviewer.md:39) forbids browser use or invented results when no cases are requested; [handoff code](/home/mark/Projects/sawmill/code/audit/src/user-testing.ts:71) implements the opt-in. The absence is therefore a configured coverage gap, not evidence that every reviewer ignored its instructions.

Specific UI deliveries expose the consequence. [#93's reviewer](/home/mark/Projects/sawmill/code/develop/.mill/logs/93/reviewer-1.jsonl.meta.json:1) passed real HTTP tests but said the buttons, Answer dialog and confirmation boxes had never been checked in a browser, despite the spec requiring desktop and 390px checks. [#92's reviewer](/home/mark/Projects/sawmill/code/develop/.mill/logs/92/reviewer-1.jsonl.meta.json:1) identified source-regex coverage instead of keyboard/phone use and warned that archive refreshes lose keyboard focus. [#49](/home/mark/Projects/sawmill/code/develop/.mill/logs/49/reviewer-1.jsonl.meta.json:1) similarly deferred the actual terminal Ctrl-click acceptance check.

There was real human phone evidence: the user explicitly accepted the earlier [#28](https://github.com/markdlabrecque/sawmill/issues/28) spike after trying it on a phone, in [this native message](/home/mark/.claude/projects/-home-mark-Projects-sawmill/f5d4448a-37a1-4c86-8e88-6a64c0eb8988.jsonl:289). That predates [#33](https://github.com/markdlabrecque/sawmill/issues/33). The later [#33 reviewer](/home/mark/Projects/sawmill/code/develop/.mill/logs/33/reviewer-1.jsonl.meta.json:1) explicitly leaves its real-phone check and newly written systemd command unverified. Inspection of that issue's nine comments found no later recorded phone/browser acceptance. The correct conclusion is missing delivery-specific evidence, not that no phone test ever happened.

Recommendation: require an explicit browser-verification decision for UI changes during ticket preparation. Capture applicable content-editor, anonymous visitor, authenticated user, keyboard and narrow-screen cases. Support a local development-server lifecycle as well as DDEV/Docker so a Node UI does not opt out simply because its development server is neither. For WordPress/Drupal, exercise editing, saving, permissions, rendered output and cache effects against the provisioned site. These are predictions of where this gap matters, not CMS failures observed in this corpus.

## What is consuming effort without enough evidence

Documentation tests can force prose to satisfy a regex rather than improve instructions. In [#91](/home/mark/Projects/sawmill/code/develop/.mill/logs/91/implementer-1.jsonl.meta.json:1), the implementer added a ticket reference to satisfy a same-line assertion; the [reviewer](/home/mark/Projects/sawmill/code/develop/.mill/logs/91/reviewer-1.jsonl.meta.json:1) explicitly recommends loosening that test. Use runnable command examples, link checks and factual review for operating documentation. Do not generalize the intentional alpha/beta and slow-run pilot tests into routine documentation testing.

Protected-test corrections are useful, but the latest six-ticket batch, 119 through 124, consumed 38 role invocations and four formal corrections. The corrections repaired fixture output truncation, null/undefined polling, contradictory slot capacity, and a command simultaneously declared allowed and denied. This supports improving fixture APIs and focused verification before dispatch, not removing protection or replacing independent review with writer self-approval. See the correction-review [119](/home/mark/Projects/sawmill/code/develop/.mill/logs/119/reviewer-2.jsonl.meta.json:1), [121](/home/mark/Projects/sawmill/code/develop/.mill/logs/121/reviewer-3.jsonl.meta.json:1), [123](/home/mark/Projects/sawmill/code/develop/.mill/logs/123/reviewer-2.jsonl.meta.json:1) and [124](/home/mark/Projects/sawmill/code/develop/.mill/logs/124/reviewer-2.jsonl.meta.json:1) outcomes.

Build reproducibility is a neglected part of evidence. Two [#97 passes](/home/mark/Projects/sawmill/code/develop/.mill/logs/97/reviewer-5.jsonl.meta.json:1) report a stale compiled `SCRATCH correction remainder` still running from `dist/test` after its source was gone. A clean compile directory and declared environment should be part of the verification command. The latest [#124 reviewer](/home/mark/Projects/sawmill/code/develop/.mill/logs/124/reviewer-2.jsonl.meta.json:1) reports two green local suites but a Mill-only 30-minute hang. Earlier worker-environment fixes improved matters; they do not establish that all environment divergence and hangs are resolved. Track failure signatures and hanging processes rather than treating a later green rerun as proof the earlier failure was harmless.

Permissions need compatibility evidence at the actual runtime boundary. Across these historical streams, 154 direct tool-result permission denials occurred in 107 distinct invocations: 129 reviewer denials, 19 implementer, 6 writer. These are exact denial messages, not incidental mentions in test output. They are not all defects or requests that should have been allowed; some combine reads with forbidden actions. The count spans older policies and is not a current failure rate. [Denial ledger](/tmp/sawmill-delivery-audit/claude-final-denials.json).

The useful next step is a small live compatibility suite for declared read/test/rebase capabilities. [#120's reviewer](/home/mark/Projects/sawmill/code/develop/.mill/logs/120/reviewer-1.jsonl.meta.json:1) says the runtime rule was only checked by a fake process using string comparison and needs a live quoted-redirection check. [#124's reviewer](/home/mark/Projects/sawmill/code/develop/.mill/logs/124/reviewer-2.jsonl.meta.json:1) documents that Claude's focused wildcard rule accepts appended flags or parent-directory paths while Pi validates arguments. Do not describe these backends as equivalent without proving the actual enforcement contract. Avoid solving legitimate verification friction with a blanket shell grant.

Measure future delivery by accepted scenarios, human interventions, repeat environment failures, review defects caught, time waiting for external systems, and corrections per change. Invocation counts alone cannot tell whether cheaper writing plus stronger review is economical. For other project types, choose a ticket-level path for executable code, documentation, migration, investigation and human acceptance; mandatory red tests cannot prove all five kinds of work.
